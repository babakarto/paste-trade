# AI agents that directly control smartphones — state as of October 2026

Scope: Claude/LLM agents driving Android over ADB and computer-use; open-source mobile-agent frameworks; OEM/platform agents (Google, Apple, Samsung, Honor, Xiaomi, Oppo, Vivo, ByteDance); what is technically possible vs blocked on iOS/Android; and buildable gaps. Research conducted 2026-10-11. Everything dated; older facts flagged.

## Key Question 1 — Notable demos/projects of Claude (or other LLMs) controlling an Android phone over ADB; what they do well / badly

### Takeaway
There is still no first-party Anthropic "Claude controls your Android phone" product: Anthropic's only shipped mobile surface is an iOS *Simulator* pane in Claude Code Desktop (public beta, July 2026), and an Android-emulator equivalent exists in the Windows build's code but is gated off. Everything on real Android phones is community work — dozens of MCP servers and CLI agents that wrap ADB (screenshot + `uiautomator dump` + `input tap`) and let Claude/GPT/Gemini act — and their consistent weak spots are latency (300–1000 ms per ADB tap, 1–5 s per UI-tree dump, plus one LLM call per step), per-step cost, a tethered PC requirement, FLAG_SECURE/black screenshots on payment pages, and prompt-injection exposure of the host machine.

### Cited Findings

**Anthropic first-party**
- On 21 July 2026 Anthropic announced Claude Code Desktop can build and launch an iOS app in Apple's Simulator, with a simulator pane beside the chat; Claude can tap, type, launch apps and take screenshots; requires Claude Desktop v1.24012.0+, a Mac with Xcode; Pro/Max/Team plans (not Enterprise); local sessions only (cloud/SSH sessions cannot reach the Mac's simulator); screenshots are sent to Anthropic; Anthropic advises not signing into real accounts on the simulated device — [MacRumors](https://www.macrumors.com/2026/07/21/claude-code-ios-simulator/); [9to5Mac](https://9to5mac.com/2026/07/21/claude-code-brings-live-ios-app-testing-into-its-mac-app/)
- A German report says the feature is limited to simulated devices; physical iPhones are not supported — [BornCity](https://borncity.com/news/claude-code-desktop-ios-simulator-fuer-ki-gesteuerte-app-entwicklung/)
- Based on reverse engineering of Claude for Windows v1.44121.4, RuntimeWire reports Anthropic has built a first-party Android Emulator integration into Claude Desktop (Windows UI, setup flow, device controls, permission system) but holds it behind a rollout capability that currently returns "disabled"; Anthropic did not comment; public docs remain iOS-only — [RuntimeWire](https://runtimewire.com/article/claude-desktop-is-ready-to-test-android-apps-whenever-anthropic-flips-the-switch) (unconfirmed by Anthropic; treat as rumor)
- A practitioner guide notes Claude Desktop has no Android simulator pane; Android work runs through the shell and ADB in chat; the emulator itself still runs on the developer's machine — [madewithlove](https://madewithlove.com/blog/the-claude-desktop-app-just-killed-fifteen-years-of-waiting-for-an-android-emulator-to-boot/)

**Community ADB/MCP bridges for Claude**
- `claude-in-android` (AlexGladkov): MCP server letting Claude take screenshots, read UI hierarchy, tap, swipe, type, launch/install apps, run shell commands; installed via `npx claude-in-android` into Claude Code — [LobeHub listing](https://lobehub.com/de/mcp/alexgladkov-claude-in-android); successor repo "claude-in-mobile" README — [Glama](https://glama.ai/mcp/servers/@AlexGladkov/claude-in-mobile/blob/af6915dd73e77ef2ea676ce543610aae1121e25e/README.md)
- `agentic-android`: LLM reads screen and acts through ADB; can use the logged-in `claude` CLI as the brain so no API key is needed — [Glama](https://glama.ai/mcp/servers/xDope7137/agentic-android)
- `adb-mcp` (FlashZ): "90 tools across 9 groups" for Claude Code Android control — [GitHub](https://github.com/FlashZ/adb-mcp)
- `Android-Debug-Bridge-MCP` (TiagoDanin) — [Glama README](https://glama.ai/mcp/servers/@TiagoDanin/Android-Debug-Bridge-MCP/blob/f565dd5e881f37ddd548d12dce1c9807e80c0cdf/README.md); `us-all/android` "Android MCP — ADB-based device, apps, UI, logcat, emulator, files, system, debug" — [getdrio](https://www.getdrio.com/mcp/io-github-us-all-android)
- `mobile-next/mobile-mcp`: ~9.0k stars, 801 forks, Apache-2.0; drives iOS and Android apps "from the native accessibility tree," no vision model by default, screenshot+coordinate fallback "only when needed"; supports iOS Simulator (xcrun simctl), real iOS over USB, Android emulator and real device via adb; Node 20+, Xcode CLT, platform-tools required; Streamable HTTP mode is unauthenticated unless `MOBILEMCP_AUTH` is set; device mirroring only in kitty-protocol terminals — [GitHub](https://github.com/mobile-next/mobile-mcp)
- `droidclaw` (unitedbyai): TypeScript/Bun agent that "turns old Android phones into AI agents" over ADB; loop = dump accessibility tree via ADB → diff vs previous screen → LLM returns think/plan/action → ADB tap/type/swipe; Workflows (JSON, AI per step) and Flows (YAML, no LLM); providers Groq/Ollama/OpenAI/Bedrock; stuck-loop detection after 3 unchanged screens, repetition and drift detection, vision fallback for webviews/Flutter/games with empty trees; weaknesses: Android only, "screen-based automation is inherently fragile and slower than API calls," requires USB debugging or ADB-over-WiFi plus a computer running Bun, every step is an LLM call; ~1,523 stars/225 forks; last commit 28 Feb 2026, v0.5.3; Show HN Feb 2026 got 3 points, 0 comments; status "Stalled" as of June 2026; MIT per website but no LICENSE file — [rywalker.com review](https://rywalker.com/research/droidclaw)
- `NeuralBridge` (Apache-2.0, Mar 25 2026): MCP server embedded *in* an Android app (Ktor HTTP server on port 7474), agent talks to the phone's WiFi IP directly, no ADB forwarding; AccessibilityService `dispatchGesture()` gives tap ~2 ms, swipe ~2 ms, text input ~1.4 ms, UI tree 18–33 ms, screenshot ~60 ms (Pixel 7/Android 14, 100 runs) vs conventional ADB tap 300–1000 ms, UI dump 1–5 s, ~100–200 ms process-spawn overhead per adb command; ADB kept as fallback (~200 ms, ~5% of ops) for force-stop, clipboard on Android 10+, package management; Google Play won't distribute automation AccessibilityServices so it is sideloaded; Android 15+ requires manual enabling of restricted accessibility settings; Android 14+ resets MediaProjection consent on restart; OpenGL/Unity/Unreal games have no tree; FLAG_SECURE banking apps block screenshots; biometric prompts cannot be automated; 30–120 s JIT cold start; no auth on the server — [HackerNoon](https://hackernoon.com/i-built-a-100x-faster-android-automation-tool-because-ai-agents-deserve-better); [GitHub](https://github.com/dondetir/NeuralBridge_mcp)
- `Android Action Kernel` claims "95% cost savings + 5x faster" vs Anthropic Computer Use via an accessibility-tree approach (vendor claim) — [GitHub](https://github.com/articulite/android-action-kernel)
- `Android-MCP` reports 2–4 s typical latency between sequential actions when using structured accessibility data — [summarised in search results](https://prompts.brightcoding.dev/blog/cursortouchandroid-mcp-llm-controlled-android-automation-without-cv-pipelines)

**Security of ADB-tethered agents**
- Paper "(A)I Sees What You Don't" (arXiv 2607.00333, July 2026, first author Zidong Zhang) tested AppAgent, AppAgentX, Mobile-Agent-v3, Open-AutoGLM and MobA with seven attacks (2–20% opacity text overlays, instructions under rounded corners/camera cutouts, fake login screen, screenshot file tampering, broadcast interception, credential capture via accessibility service, host command injection). Every framework was susceptible to ≥6 of 7. Host command injection (launch Windows Calculator) succeeded 20/20 trials on each of four frameworks (80/80); Open-AutoGLM resisted because it neutralised shell metacharacters; screenshot tampering hit four (MobA streams screenshots directly); the accessibility-service credential attack hit all five. Mitigations: pass host commands as arg lists, stream screenshots through memory, authenticated text-input broadcasts, confirm sensitive actions based on the *proposed action* not the model's reading of a possibly poisoned image — [vibegraveyard summary](https://vibegraveyard.ai/story/android-ai-agents-invisible-prompt-injection-host-command/); [arXiv](https://arxiv.org/abs/2607.00333)

**Anti-bot / captcha anecdote**
- A Chinese-language developer post describes an ADB agent using a cloud vision model to solve slider/icon captchas; the several-second model delay appeared to trigger the target app's anti-bot checks; developer considered smaller local models to reduce delay — [80aj.com](https://www.80aj.com/2026/08/25/captcha-agent-delay-solution/) (single anecdote)

### Inferences
- The "Claude + ADB" space is commoditised plumbing: at least six functionally equivalent MCP servers exist. Differentiation has moved to (a) on-device execution to kill ADB latency, (b) untethered operation, (c) safety/injection hardening — none of which the popular wrappers do well.
- Anthropic's trajectory (iOS Simulator pane shipped; Android emulator gated) suggests a first-party *developer-testing* emulator integration is likely, but nothing indicates a consumer "control my real phone" product.
- Because every step is an LLM round-trip, agents behave bot-like (multi-second pauses between taps), which is exactly the signal anti-bot systems and Chinese super-apps key on (see ByteDance case, Q3).

### Gaps
- No official Anthropic statement on Android emulator support; RuntimeWire claim unverified.
- No dated tweet/blog demos of Claude specifically driving a *physical* Android phone with measurable outcomes could be located beyond README-level claims; HN engagement for these tools is minimal (droidclaw's Show HN: 3 points).
- Star counts for `claude-in-android`, `adb-mcp`, `agentic-android` were not shown on the aggregator pages fetched.

## Key Question 2 — Open-source mobile agent frameworks: maturity, benchmarks, and what their issues/discussions say is missing

### Takeaway
The field has consolidated around five serious projects — Mobilerun/DroidRun (9.6k★, VC-funded, 91.4% AndroidWorld claim), Zhipu's Open-AutoGLM (26.4k★, 9B model, ADB/HDC, China-app focused), Alibaba's Mobile-Agent/GUI-Owl (9.3k★, model-centric research), mobile-next/mobile-mcp (9.0k★, tree-first MCP) and minitap mobile-use (2.5k★) — plus a long tail of stalled or hobby projects (AppAgent 6.8k★ but inactive since Mar 2025, droidclaw, Blurr/Panda, PokeClaw). AndroidWorld (116 tasks/20 apps) is effectively saturated at 91–98% by vendor-reported runs, yet an independent 65-task run with Claude Sonnet 4.5 got only 43% for the best framework at ~$0.075 and ~78 s per task, so real-world reliability, cost per step, login/2FA takeover, and iOS parity remain the openly acknowledged holes.

### Cited Findings

**Mobilerun (formerly DroidRun) — github.com/droidrun/mobilerun**
- 9.6k stars, 1.0k forks, MIT; controls Android and iOS; `mobilerun setup` installs the "Mobilerun Portal" app and enables its accessibility service; Portal provides UI trees, screenshots, text input, gestures, app launch, device state; agent can combine trees + screenshots or go screenshot-only (for apps without tree info); Python ≥3.11,<3.14; iOS via separate "iOS Portal"; README badge "Benchmark 91.4%"; Mobilerun Cloud offers Personal / Cloud Phone (Hosted) / Physical Phone (Hosted) devices, no prices listed — [GitHub](https://github.com/droidrun/droidrun)
- Rename: Smithery/mcp.directory list the package as `mobilerun` with a `mobilerun/` source path while other pages still say droidrun — [Smithery](https://smithery.ai/skills/droidrun/droidrun-docs)
- Open-sourced April 2025; Product Hunt launch claimed 63% on 116 AndroidWorld tasks vs ~30% for most others (maker's claim) — [Product Hunt](https://www.producthunt.com/p/droidrun-framework-for-mobile-agent/droidrun)
- Raised €2.1M pre-seed (23 July 2025) to "scale mobile-native AI agent infrastructure" — [tech.eu](https://tech.eu/2025/07/23/droidrun-raises-eur21m-pre-seed-to-scale-mobile-native-ai-agent-infrastructure/)
- Mobilerun benchmark page now claims "98.24% mean official score across 133 iOSWorld tasks and 116 successful AndroidWorld trajectories" (asset paths dated 2026-09-25), with no models or methodology shown — [mobilerun.ai/benchmark](https://mobilerun.ai/benchmark)
- Architecture per third-party summary: reasoning mode (Manager plans, Executor acts) and direct mode (CodeActAgent generates/runs Python); supports OpenAI, Anthropic, Gemini, Ollama, DeepSeek; tracing via Arize Phoenix — [jimmysong.io](https://jimmysong.io/ai/droidrun)

**Open-AutoGLM (Zhipu / Z.ai) — github.com/zai-org/Open-AutoGLM**
- 26.4k stars, 4.1k forks, Apache-2.0; model AutoGLM-Phone-9B (structure shared with GLM-4.1V-9B-Thinking) plus a Multilingual variant; Android via ADB, HarmonyOS NEXT via HDC; text input requires the ADB Keyboard IME; iOS only via a separate WebDriverAgent guide; 50+ Chinese Android apps, 60+ HarmonyOS apps; self-host needs vLLM/SGLang with 24 GB+ VRAM (~20 GB download) or use Zhipu/ModelScope APIs; built-in sensitive-operation confirmation and a `Take_over` action for login/verification codes (custom `confirmation_callback`/`takeover_callback`); known failure modes: black screenshots on payment/password/banking pages (agent detects and requests takeover), some devices need "USB debugging (security settings)" too, TCP/IP debugging disabled after reboot, 100-step default cap, Windows gbk UnicodeEncodeError, non-TTY EOF errors; "research and learning only" — [GitHub](https://github.com/zai-org/Open-AutoGLM)
- Open-sourced 9 Dec 2025, framed as a response to the ByteDance privacy backlash; "currently supporting only Android devices" at launch — [TechNode](https://technode.com/2025/12/09/zhipu-ai-open-sources-autoglm-an-ai-agent-model-capable-of-full-phone-operation/); [SCMP](https://www.scmp.com/tech/tech-trends/article/3335746/chinas-zai-open-sources-ai-agent-tool-phones-after-bytedance-privacy-backlash)

**Mobile-Agent family (Alibaba X-PLUG) — github.com/X-PLUG/MobileAgent**
- 9.3k stars, 930 forks; lineage: Mobile-Agent v1 (ICLR 2024 WS), v2 (NeurIPS 2024), Mobile-Agent-E (arXiv 2501.11733), PC-Agent (ICLR 2025 WS), GUI-Owl + Mobile-Agent-v3 (released 20 Aug 2025, arXiv 2508.15144), GUI-Critic-R1 (NeurIPS 2025), UI-S1 (ACL 2026), GUI-Owl-1.5 (14 Feb 2026, arXiv 2602.16855) with 2B/4B/8B/32B/235B Instruct and Thinking checkpoints; Mobile-Agent-v3.5 preprint; AndroidWorld eval code linked but scores only in an image; "SOTA on 20+ GUI benchmarks" claim with no table on README — [GitHub](https://github.com/X-PLUG/MobileAgent)

**AppAgent (Tencent QQ GY Lab)**
- ~6.8k stars, ~750 forks, MIT; screenshots labelled and sent to a multimodal LLM, actions executed via ADB; CHI 2025 paper; "active maintenance through March 2025" (i.e., now stale) — [Trendshift](https://trendshift.io/repositories/20089); [Bright Coding](https://converter.brightcoding.dev/blog/tencentqqgylabappagent-llm-powered-smartphone-automation)

**minitap-ai/mobile-use**
- Open-source Python framework for agents operating real Android and iOS apps; 2.5k stars / 212 forks (aggregator); Android via ADB + UIAutomator2, newer docs describe a "Screen API", "Hardware Bridge" and actions via Maestro; vendor claims 100% on 116 AndroidWorld tasks (self-reported); last activity seen March 2026 — [bytenote](https://bytenote.net/article/mobile-use-ai-phone-automation); [minitap docs](https://docs.minitap.ai/mobile-use-sdk/core-concepts/agent); [minitap blog](https://minitap.ai/magazine/cursor-alternative-mobile-real-device-testing)

**Blurr / Panda (Ayush0Chaudhary/blurr)**
- Kotlin, MIT, ~905–946 stars; on-phone Android AccessibilityService reads the UI hierarchy and performs taps/swipes; "Brain" is Gemini via API key (so not fully on-device); "Operator" executor with a "Notepad" memory; needs API 26+; last push ~13 Jan 2026 — [sourcepulse](https://www.sourcepulse.org/projects/13107005); [dev.to](https://dev.to/iamvaar/i-built-an-opensource-android-ai-automation-agent-1k0i)

**PokeClaw (agents-io/PokeClaw)** — runs Gemma 4 fully on-device via LiteRT-LM with native tool calling; reads UI tree, tools tap/swipe/type/open app/send message, executes via Accessibility Services; Android 9+ (API 28); ~67–69 stars, created days before Oct 2026 — [allclaw](https://allclaw.org/entry/pokeclaw); [sourcepulse](https://www.sourcepulse.org/projects/27635808)

**Open-Interface** — appeared only as a desktop (PC) automation project in results, not an Android agent; no Android-specific source found.

**Benchmarks**
- AndroidWorld: 116 hand-crafted tasks across 20 apps, dynamically parameterised into "millions of unique task variations"; emulator launched with `-grpc 8554` to talk to an accessibility-forwarding app; actions via AndroidEnv; 948 stars; launch paper's best baseline was 30.6% — [GitHub](https://github.com/google-research/android_world); [benchlm](https://benchlm.ai/benchmarks/androidworld)
- Leaderboard snapshots disagree: benchmarklist pass@1 top ≈97.4% (sampled 2026-06-01); AskUI May 2026 snapshot: AGI-0 97.4%, AskUI 94.8%, DroidRun 91.4%, human baseline 80.0%; BenchLM July 29 2026 open-model snapshot: Qwen3.7 Plus 81.0%, Holo3.1-35B-A3B 79.3%, Holo3.1-4B 71.0% — [benchmarklist](https://benchmarklist.com/benchmarks/androidworld/); [AskUI](https://www.askui.com/benchmarks/index.html); [benchlm](https://benchlm.ai/benchmarks/androidworld)
- An April 2026 commentary calls AndroidWorld "effectively solved" at 91% — [agentmarketcap](https://agentmarketcap.ai/blog/2026/04/06/androidworld-91-mobile-agents-benchmark-saturation-enterprise-consumer); harder successor MobileWorld tops out around 51.7% (GPT-5) — [benchmarklist MobileWorld](https://benchmarklist.com/benchmarks/mobileworld/)
- Independent AIMultiple test (updated 9 June 2026): 65 AndroidWorld tasks, Claude Sonnet 4.5 for all agents, Pixel 6 emulator (Android 13). Success: DroidRun 43%, Mobile-Agent (M3A) 29%, AutoDroid 14%, AppAgent 7%. On the single task all four completed (10 runs each): DroidRun $0.075 / ~3,225 tokens / 78 s; Mobile-Agent $0.025 / ~1,130 tokens / 66 s; AutoDroid $0.017 / ~765 tokens / 57 s; AppAgent $0.90 / ~2,346 tokens / 180 s. AppAgent "struggled with coordinate calculations and identifying UI elements"; screenshot-heavy approach drives cost and latency — [AIMultiple](https://aimultiple.com/mobile-ai-agent)

### Inferences
- The gap between vendor benchmark claims (91–100%) and the independent 43% run means AndroidWorld numbers are not a reliable guide to production reliability; the benchmark's 20 pre-installed open-source apps (no login, no captcha, no ads, no network flakiness) are the friendly case.
- Accessibility-tree-first designs (DroidRun, mobile-mcp, AutoDroid) win on success and speed over screenshot-first designs (AppAgent), but pay in tokens when the tree is verbose; nobody has shipped a good tree-compressor/router.
- Every mature framework still needs: a PC in the loop (ADB), human takeover for login/2FA/captcha, and a payment stop. These are the same three gaps the ByteDance and Google rollouts also hit.
- Research leadership has shifted to model-centric Chinese labs (Alibaba GUI-Owl-1.5 with 2B–235B checkpoints; Zhipu AutoGLM-Phone-9B), while Western projects are harness-centric and model-agnostic.

### Gaps
- Could not access GitHub Issues/Discussions text directly for DroidRun, Open-AutoGLM or mobile-mcp (only READMEs); "what's missing" is inferred from READMEs, the independent benchmark and reviews, not issue trackers.
- No Reddit threads with first-hand cost/latency complaints surfaced for these specific tools; the only quantified cost data is AIMultiple's single-task measurement.
- Mobilerun's 91.4%/98.24% claims have no published methodology or model list.
- "Panda" and "Open-Interface" as distinct *phone* agents: Panda = Blurr; Open-Interface found only as a desktop tool.

## Key Question 3 — What Google, Apple, Samsung and Chinese OEMs have shipped for cross-app agentic actions, and documented limits

### Takeaway
Google is the only Western platform owner with a shipped (beta) cross-app agent: since 25 Feb 2026 Gemini on Galaxy S26/Pixel 10 can run food-delivery, grocery and rideshare tasks in a background "secure virtual window" via a UI-automation framework, plus structured AppFunctions (Android 16 API + Jetpack alpha, EXECUTE_APP_FUNCTIONS-gated, small developer cohort, broadening in Android 17). Apple has shipped nothing agentic: iOS 26.4 (24 Mar 2026) did not include the new Siri, and the on-screen-aware, App-Intents-driven Siri announced at WWDC on 8 June 2026 is for iOS 27 this fall. Samsung piggybacks on Gemini/AppFunctions (Gallery) and a Bixby "device agent" beta. Chinese OEMs (Honor YOYO, Xiaomi Super XiaoAI, Vivo Jovi, ByteDance/Nubia Doubao) ship system-level GUI agents in China, but ByteDance's rollout showed the limit: WeChat, Alipay, Taobao and banks blocked it within days.

### Cited Findings

**Google / Android**
- 25 Feb 2026 Android Developers Blog (Matthew McCullough): AppFunctions = platform API + Jetpack library exposing "self-describing functions that agentic apps can discover and execute via natural language," executed locally on-device "rather than on a server" (contrast with MCP); Gemini "can already automate tasks in Calendar, Notes, and Tasks apps on devices from multiple manufacturers"; Samsung Gallery with Gemini on Galaxy S26, expanding to One UI 8.5+; UI automation framework "in development," early preview on Galaxy S26 and select Pixel 10, triggered by long-pressing power, beta in the Gemini app starting with "a curated set of food delivery, grocery, and rideshare apps in the US and Korea"; users monitor via notifications or "live view," can take manual control, and get alerts before sensitive actions such as purchases; developers need no code; Google is working with "a small set of app developers" and will share more "later this year"; Android 17 to broaden both — [Android Developers Blog](https://android-developers.googleblog.com/2026/02/the-intelligent-os-making-ai-agents.html)

## Key Question 4 — Platform-policy and technical blockers (Play Accessibility policy, iOS sandbox, ADB/PC tether, Android 15+ restrictions, Shizuku/root)

### Takeaway
On Android the hard blocker is policy, not capability: Play's Permissions policy now "strictly prohibits" any AccessibilityService use that lets an app "autonomously start, plan, and carry out actions," allowing only deterministic user-scripted automation or verified accessibility tools — so an LLM phone agent cannot be distributed via Play and must be sideloaded, where Android 13+ restricted-settings friction, FLAG_SECURE black screens, MediaProjection consent resets and biometric prompts remain. ADB avoids the policy but requires a PC (or a wireless-debugging pairing that is lost on reboot via Shizuku); a rumoured Google restriction on on-device ADB loopback is unconfirmed. On iOS, no public API allows a third-party process to tap/screenshot another app: control runs through WebDriverAgent/XCUITest from a Mac, breaks on iOS updates, and sees nothing in WebViews/Flutter; the sanctioned path is App Intents + Shortcuts.

### Cited Findings

**Google Play policy (current text)**
- Only services "designed to help people with disabilities access their device" may declare `isAccessibilityTool`; they must describe the core feature, disability types, target users and supply a video; Android 12+ targets also need the Permission Declaration Form. Non-accessibility apps must show an in-app prominent disclosure (in normal use, describing data accessed/shared, affirmative consent, separate from other disclosures) and complete a declaration. "The policy strictly prohibits any use of the API that lets an app autonomously start, plan, and carry out actions or decisions. Deterministic, rule-based automation, where a person defines a fixed script, is permitted. Verified accessibility tools may use autonomous functionality if it serves their core purpose." Named non-accessibility examples: antivirus, automation tools, assistants, monitoring apps, cleaners, password managers, launchers. Deceptive/undeclared use → suspension or termination — [Google Play Permissions policy](https://support.google.com/googleplay/android-developer/answer/10964491)
- History: 2017 Google threatened removal of non-accessibility uses (Tasker, LastPass named) then backed off; 2022 banned Accessibility-based call recording — [XDA](https://www.xda-developers.com/google-trying-limit-apps-accessibility-service/); [MobileSyrup](https://mobilesyrup.com/2022/04/22/google-introduces-new-play-store-policy-banning-third-party-call-recording-apps/)
- Practitioner confirmation: "Google Play won't distribute apps that use AccessibilityService for automation, so NeuralBridge is sideloaded"; Android 15+ requires manually enabling restricted accessibility settings; Android 14+ resets MediaProjection consent on app restart — [HackerNoon/NeuralBridge](https://hackernoon.com/i-built-a-100x-faster-android-automation-tool-because-ai-agents-deserve-better)

**Android technical limits**
- FLAG_SECURE: banking apps block screenshots (NeuralBridge); Open-AutoGLM reports black screenshots on payment/password/banking pages and hands off to human — [GitHub Open-AutoGLM](https://github.com/zai-org/Open-AutoGLM)
- No accessibility tree for OpenGL/Unity/Unreal games; biometric prompts cannot be automated — [HackerNoon](https://hackernoon.com/i-built-a-100x-faster-android-automation-tool-because-ai-agents-deserve-better)
- ADB latency: tap 300–1000 ms, UI dump 1–5 s, 100–200 ms per adb process spawn; in-process AccessibilityService: ~2 ms tap, 18–33 ms tree — same source
- ADB text input needs a special IME (ADB Keyboard); some OEMs require "USB debugging (security settings)" for input injection; TCP/IP debugging drops after reboot — [Open-AutoGLM](https://github.com/zai-org/Open-AutoGLM)
- Shizuku: wireless-debugging start works on Android 11+ without a computer, but pairing is one-time while the startup must be repeated after every reboot — [Shizuku manual](https://shizuku.rikka.app/guide/setup/); some vivo/iQOO builds block the ADB route regardless, forcing Accessibility fallback; Android 17 adds local-network permission prompts that may affect pairing — [Octoclip docs](https://docs.octoclip.app/features/source/background-monitoring/android/device-compatibility/)
- Rumour: Google "may" block on-device ADB loopback that Shizuku relies on — based on a single Issue Tracker comment; as of July 2026 no official statement, no identified code change, no timeline — [braindetox](https://braindetox.kr/en/posts/android_adb_restriction_2026.html)
- Prompt-injection and host-compromise risk of PC-tethered agents (80/80 command-injection successes; all five frameworks vulnerable to accessibility credential capture) — [arXiv 2607.00333](https://arxiv.org/abs/2607.00333)
- Anti-bot detection: multi-second LLM pauses flagged as automation (captcha anecdote) — [80aj](https://www.80aj.com/2026/08/25/captcha-agent-delay-solution/); platform risk controls flagged Doubao's human-like taps as bot activity (WeChat statement) — [SCMP](https://www.scmp.com/business/china-business/article/3335404/bytedances-agentic-ai-smartphone-dials-digital-backlash-chinas-top-apps)

**iOS technical limits**
- "Due to iOS's strict security, direct input simulations or screenshot captures via public APIs or shell commands are prevented. WebDriverAgent circumvents these limitations by launching an HTTP server on the device" exposing XCUITest over REST; UI automation must be enabled in Developer Settings before installing the WDA runner; WDA "shares all the known problem[s] that are present in XCTest"; "when iOS updates, WebDriverAgent breaks"; accessibility-layer tools miss WebViews, third-party SDK elements and Flutter — [Appium docs](https://appium.readthedocs.io/en/stable/en/advanced-concepts/wda-custom-server/); [Appium XCUITest driver](https://appium.readthedocs.io/en/latest/en/drivers/ios-xcuitest/); [Drizz](https://www.drizz.dev/post/ios-automation-testing-tools-in-2026); [Jean Galea](https://jeangalea.com/control-automate-iphone-webdriveragent/)
- All iOS agent paths found (mobile-mcp real device, Open-AutoGLM iOS guide, Mobilerun iOS Portal) depend on WebDriverAgent/XCUITest and a Mac — [mobile-mcp](https://github.com/mobile-next/mobile-mcp); [Open-AutoGLM](https://github.com/zai-org/Open-AutoGLM)
- Anthropic's own iOS integration is Simulator-only, physical iPhones unsupported — [BornCity](https://borncity.com/news/claude-code-desktop-ios-simulator-fuer-ki-gesteuerte-app-entwicklung/)
- Apple's sanctioned agent surface is App Intents (Apple Intelligence runs the model and routes to your app) and the on-device Foundation Models framework (3B, 4k context, no vision until iOS 27) — [MacStories](https://www.macstories.net/stories/ios-and-ipados-26-the-macstories-review/8)

**Google's own answer**
- Platform-run UI automation in a background virtual window with curated apps, live view, take-over and purchase alerts — [Android Developers Blog](https://android-developers.googleblog.com/2026/02/the-intelligent-os-making-ai-agents.html); EXECUTE_APP_FUNCTIONS gating for structured calls — [developer.android.com](https://developer.android.com/reference/kotlin/androidx/appfunctions/AppFunctionManager)

### Inferences
- The viable untethered Android architecture today is: sideloaded APK hosting an AccessibilityService (+ optional MediaProjection) exposing an MCP/HTTP endpoint — fast (ms-level actions) but non-Play-distributable, must be re-authorised through restricted settings, and blind on FLAG_SECURE/game surfaces. Everything else needs a PC or a Shizuku pairing that dies on reboot.
- Policy risk is asymmetric: Google itself now does autonomous UI automation, but Play explicitly forbids third parties from doing the same via AccessibilityService; a third-party agent therefore competes from outside the store.
- On iOS there is no realistic path for an independent developer to build a GUI-driving agent for end users; the opportunities are App Intents tooling, Shortcuts orchestration, and Mac-tethered developer/QA agents.
- Background iOS execution limits were not documented in sources found, but every iOS agent architecture observed runs the controller off-device (Mac), which is itself evidence of the constraint.

### Gaps
- No primary Apple documentation on background-execution limits for an on-device agent was retrieved.
- Exact Android 13–16 "restricted settings" behaviour for sideloaded AccessibilityServices not fetched from AOSP docs; relied on practitioner report.
- No evidence found of Play enforcement actions against LLM phone agents specifically (likely because none have tried to list).

## Key Question 5 — Specific, buildable gaps an independent developer could plausibly fill now

### Takeaway
The evidence points to seven concrete, underserved layers: (1) untethered on-phone control (AccessibilityService-hosted MCP/HTTP server with auth, proper restricted-settings onboarding, and a Shizuku/wireless-ADB fallback for what Accessibility can't do); (2) a compact, deterministic UI-tree→action layer with element IDs, diffing and token compression (DroidRun's 3,225 tokens/step vs AutoDroid's 765 shows the headroom); (3) a hardened safety layer — action-based confirmation, host-command sanitisation, screenshot streaming, FLAG_SECURE/biometric/2FA takeover; (4) a cost/latency router that runs a small on-device model (Gemma 4 / GUI-Owl-1.5-2B/4B / Holo3.1-4B) for routine steps and escalates to a frontier model; (5) verification/undo and audit logging; (6) app-side agent readiness — AppFunctions/App Intents authoring and testing tools, since Google's and Apple's agents will only reach apps that expose functions; (7) realistic benchmarks beyond saturated AndroidWorld (login, captcha, ads, network failures, real OEM skins).

### Cited Findings (evidence each gap is real)
- Tethering: droidclaw "requires USB debugging or ADB over WiFi and a computer running Bun" — [rywalker](https://rywalker.com/research/droidclaw); Open-AutoGLM requires PC + ADB/HDC — [GitHub](https://github.com/zai-org/Open-AutoGLM); mobile-mcp requires Node + platform tools — [GitHub](https://github.com/mobile-next/mobile-mcp)
- Only on-phone server found (NeuralBridge) ships with no authentication and 30–120 s cold start; token auth "on the roadmap" — [HackerNoon](https://hackernoon.com/i-built-a-100x-faster-android-automation-tool-because-ai-agents-deserve-better)
- Token/cost spread across frameworks on the same task with the same model (765 → 3,225 tokens; $0.017 → $0.90) — [AIMultiple](https://aimultiple.com/mobile-ai-agent)
- Accessibility-tree approach claimed 95% cheaper/5× faster than screenshot computer-use (vendor) — [android-action-kernel](https://github.com/articulite/android-action-kernel)
- Safety gaps: 7-attack study; mitigations (arg-list commands, memory-streamed screenshots, authenticated input broadcasts, action-based confirmation) are specific and unimplemented in 4 of 5 frameworks — [arXiv 2607.00333](https://arxiv.org/abs/2607.00333)
- Human-takeover primitives exist only in Open-AutoGLM (`Take_over`, `confirmation_callback`) — [GitHub](https://github.com/zai-org/Open-AutoGLM); Google's agent hands payment back to the human — [heise](https://heise.de/-11191564)
- Small-model viability: GUI-Owl-1.5 released in 2B/4B/8B (Feb 2026) — [X-PLUG](https://github.com/X-PLUG/MobileAgent); Holo3.1-4B at 71.0% AndroidWorld — [benchlm](https://benchlm.ai/benchmarks/androidworld); PokeClaw runs Gemma 4 fully on-device via LiteRT-LM with tool calling — [allclaw](https://allclaw.org/entry/pokeclaw); Apple on-device model is 3B/4k-context/no vision — [MacStories](https://www.macstories.net/stories/ios-and-ipados-26-the-macstories-review/8)
- App-side readiness: Google is working with only "a small set of app developers" and will publish AppFunctions guidance "later this year"; Jetpack `androidx.appfunctions` still at 1.0.0-alpha — [Android Developers Blog](https://android-developers.googleblog.com/2026/02/the-intelligent-os-making-ai-agents.html); [reference](https://developer.android.com/reference/kotlin/androidx/appfunctions/AppFunctionManager); Apple's iOS 27 Siri acts only on App-Intents-adopting apps — [TechCabal](https://techcabal.com/2026/06/08/wwdc-2026-announcements/)
- Benchmark saturation vs reality: 91–98% vendor AndroidWorld claims vs 43% independent; MobileWorld top 51.7% — [benchmarklist](https://benchmarklist.com/benchmarks/androidworld/); [AIMultiple](https://aimultiple.com/mobile-ai-agent); [MobileWorld](https://benchmarklist.com/benchmarks/mobileworld/)
- Anti-bot/ecosystem resistance makes "undetectable, human-paced" execution and app-allow-lists a product requirement — [SCMP Doubao](https://www.scmp.com/business/china-business/article/3335404/bytedances-agentic-ai-smartphone-dials-digital-backlash-chinas-top-apps)
- Stalled/abandoned projects leave users without maintained options: droidclaw stalled (Feb 2026), AppAgent inactive since Mar 2025, Blurr last push Jan 2026 — [rywalker](https://rywalker.com/research/droidclaw); [Bright Coding](https://converter.brightcoding.dev/blog/tencentqqgylabappagent-llm-powered-smartphone-automation); [sourcepulse](https://www.sourcepulse.org/projects/13107005)

### Inferences (gap list, ranked by evidence strength)
1. **Phone-as-MCP-server, untethered and secure** — NeuralBridge proved ms-level latency is achievable on-device, but shipped without auth or Play-compatible onboarding; nobody offers a polished sideload+restricted-settings+QR-pairing flow with mTLS/token auth, Tailscale-style reachability, and a Shizuku/wireless-ADB side-channel for force-stop/package ops.
2. **Deterministic UI-tree action layer** — stable element IDs, tree diffing, semantic compression (strip decorative nodes, dedupe lists), and "Flows"-style replay so a successful LLM run becomes a zero-LLM script (droidclaw's Flows idea, mostly unmaintained). Direct lever on the 4× token spread.
3. **Safety/verification/undo** — action-schema-based confirmation (not screenshot-reading), sensitive-app allow/deny lists, FLAG_SECURE/biometric/2FA takeover UX, audit log with before/after tree snapshots, and reversible-action heuristics. Explicitly recommended by the July 2026 paper and implemented nowhere fully.
4. **Small-model router** — on-device 2–4B GUI model (GUI-Owl-1.5-2B/4B, Gemma 4 via LiteRT-LM, Holo3.1-4B) for grounding/routine steps, frontier model only for planning/recovery; target <$0.01 and <10 s per step vs today's $0.075/78 s.
5. **AppFunctions / App Intents authoring + test harness** — since Google/Apple agents only reach exposed functions and the Jetpack lib is alpha with docs promised "later this year," a generator/validator/local-agent-simulator for `@AppFunction` and App Intents is a timely developer-tool gap.
6. **Realistic benchmark + evaluation harness** — login, OTP, captcha, ads, flaky network, OEM skins, real Play Store apps; AndroidWorld is saturated and MobileWorld is nascent.
7. **iOS**: no GUI-agent opportunity for end users; buildable gaps are Mac-tethered QA agents (Anthropic covers Simulator only; physical devices via WDA remain unpolished) and Shortcuts/App-Intents orchestration.

### Gaps
- No market-size or pricing data for mobile-agent cloud offerings (Mobilerun Cloud lists tiers but no prices).
- No documented user demand signals (e.g., issue counts, Reddit threads) for specific missing features; the gap list is inferred from architecture limits, benchmark data, and the one security study.
- Unknown whether Google's Android 17 UI-automation framework will open to third-party agent apps (would partially close gap 1 on Pixel/Samsung); Google said only "more developers and device manufacturers."
